# 语义切段：现存问题清单（待调研）

> 给接手调研的人/agent 看。代码 `semantic_seg.py`（核心）+ `server.py`（网页 demo）+ `benchmark_semantic.py`（评测）。
> 所有数字都来自本机实测（Windows，Python 3.11，sherpa-onnx 2.0.1），复现命令见文末。

## P0 — 影响能不能用

### 1. 判定结果强依赖 ASR 有没有标点

`completeness()` 里最强的一条完整信号是「句末是 `。？！`」。Paraformer 不产标点，这条永远不触发，剩下只能靠词表后缀匹配。

- 实测同一段 272s 真人独白：SenseVoice 决策 **94% 完整句 / 等待 0.3s ×52**；Paraformer 决策 **10% / 等待 0.6s ×35**。
- 也就是说：**换 ASR 模型 → 切段行为整体变掉**，而这两件事在架构上不应该绑在一起。

**调研方向**：断句决策能否不依赖标点？例如用韵律特征（句尾基频下降、末字时长延长、能量衰减）做一个轻量分类器；或对无标点文本做句法/依存分析判断谓语是否完整。
**验收**：Paraformer 决策的「完整句占比」从 10% 提到 70%+，且 24 句评测集不低于 15/24。

### 2. 语气词优先级压过承接词，词表还不一致

判定顺序是「先查未完成词表，再查语气词表」，但**后缀匹配是精确匹配**，所以「承接词 + 语气词」会漏掉。

`_INCOMPLETE_TAILS` 里有「然后呢」，也有「所以」「但是」，**但没有「所以呢」「但是呢」**——同一个现象只覆盖了一种说法：

```
semantic_seg.completeness("所以。")     -> incomplete   ✅
semantic_seg.completeness("所以呢。")   -> complete     ❌ 应为 incomplete
semantic_seg.completeness("但是呢。")   -> complete     ❌ 应为 incomplete
semantic_seg.completeness("然后呢。")   -> incomplete   ✅（「然后呢」在表里）
```

（「因为呢。」恰好被因果规则（有「因为」无「所以」）拦住了，所以例子只举所以/但是。）

真实影响（雷军 272s，两模型都中）：

- SenseVoice 第 51 句 `260.4–263.0s` 「是正慑。**所以呢**。」→ 判「完整句·等 0.3s」，实际后面还接着「我就下定决心认认真真读书」。
- Paraformer 第 39 句 `256.8–263.0s` 同样以「所以呢」结尾被放过。

**调研方向**：不要靠穷举词表。更通用的做法是**先把句尾语气词剥掉再匹配承接词**（`所以呢` → `所以` → incomplete；`朋友呢` → `朋友` → 无承接词 → 再查语气词 → complete）。验证一下这个归一化会不会引入新误判。
**验收**：上面三行 `completeness()` 输出变成 incomplete / incomplete / incomplete，且 24 句评测集不掉分。

### 3. 语义层只能合并、不能拆分

`segment()` 只做合并，切点完全由 VAD 细切的片段边界决定。Silero VAD 对 0.5s 左右的停顿不敏感（`min_silence` 调到 0.1 也只多切出几个片段），**两句已经粘在一个片段里，语义层救不回来**。

- 实测：272s 音频只用 VAD 细切得到 **75 片段**（相当于每 3.6s 一个），语义层把 42–54 个片段合并成句。
- 后果：粘连只能靠 20s 上限兜底（见问题 4）。

**调研方向**：能不能在片段内部做二次切分？例如对长片段做基于停顿强度的能量谷检测，或用一个「句边界预测」模型对片段内部逐帧打分。
**验收**：粘连数从 3 降到 1（24 句集），且不引入新的切断。

### 4. 20s 硬上限会把两句话塞进一句

`SemanticParams.max_utt = 20.0`，超过就强制断，`reason=max_len`。

- 实测第 3 句 `46.9–66.9s` 正好 20.0s，里面装了「前三次因为疫情…现场人很少。这是第四次。我们仔细想了想…聚一聚。」**至少两句**。
- 触发原因：雷军语速快，句与句之间的静音常小于 0.3s，`gap >= short_wait` 不成立就一直合并。

**调研方向**：上限触发时能否回溯找内部最像句尾的位置（按能量谷 / 标点 / 语气词）再切一刀，而不是硬切在 20.0s。
**验收**：上限截断的句子数从 1 降到 0，且该句不再包含两个以上的句末语气词。

## P1 — 影响好不好用

### 5. 词表法的固有天花板

```
completeness("我们就在北京的")     -> uncertain   ❌
completeness("我们就在北京的。")    -> complete     ❌ 应为 incomplete（「的」悬空，带标点也救不了）
completeness("谢谢大家")          -> uncertain   ❌ 其实是完整句
completeness("谢谢大家。")         -> complete     ✅ 靠句末标点兜住（表里只有「谢谢」）
```

注意两组不一样：「的」悬空**带标点也判错**，是真正的词表缺口；「谢谢大家」只在没标点时才错，属于问题 1 的下游症状。「我想听」这种动词悬空同样判不了。口语的多样性远超手写词表。

**调研方向**：评估「小模型分类器」替代规则表（输入：累计文本 + 可选韵律特征；输出：complete/incomplete/uncertain）。要求能跑端侧 ONNX、支持中文、体积 < 20MB。
**验收**：24 句集 ≥ 18/24，且真人复测集（见问题 9）不低于规则法。

### 6. 句首承接规则覆盖窄

`_CONTINUE_HEADS` 只收「然后/所以/但是/可是/不过/而且/并且/以及/或者/因此/那就/接着/之后/顺便/结果/就/再」。实测漏掉的典型情况：

- 「两个月前。｜**我**参加了今年武汉大学的毕业典礼」
- 「作为校友。｜**被**母校邀请。在毕业典礼上致辞」
- 「今年呢是。｜**武汉大学**建校一百三十周年」

主语开头、被动开头都不在表里。这三处占了 SenseVoice 那份输出里最主要的切断（抢话）错误。

**调研方向**：超出词表范围——能否用「上一句是否语法完整」（依存树根节点/缺失宾语）来判断该不该并回，而不是看下一句开头的词。
**验收**：雷军 272s 里明显的句内切断从 3–4 处降到 ≤1 处。

### 7. 实时性与端侧成本没测

- 决策需要**逐片段识别**：272s 音频 → 75 片段 → SenseVoice 决策 9.2s（34ms/秒音频），Paraformer 2.7s（10ms/秒）。文档另一处记录 60ms/秒。
- 实时链路里每个片段要「先识别完 → 才能判断 → 才能决定等多久」，这笔延迟直接加在响应时间上（除等待时长之外）。
- 目前只有离线实现，`segment()` 注释说"可直接搬到端侧常驻链路"，但**没有流式版本，也没在目标芯片上测过 RTF**。

**调研方向**：① 流式实现（片段结束即决策，不要等整段音频）；② 片段级 RTF 在目标芯片上实测；③ 能否复用决策时的识别结果作为最终文本（现在整句会再识别一遍，等于双份算力）。
**验收**：给出目标芯片上「一句话说完 → 输出文本」的端到端延迟分解（VAD 判停 + 片段识别 + 决策 + 整句重识别）。

### 8. 端侧内存 vs 质量的取舍没算清

| 方案 | 常驻体积 | 决策质量（24 句） |
|---|---|---|
| SenseVoice 决策（现方案） | 228MB（+ 主 ASR 若也用 SenseVoice 则不额外占） | 15/24 |
| Paraformer 决策 | 78MB | 8/24 |
| Paraformer + CT-Transformer 标点模型 | 78+72=150MB | 14/24 |

如果端侧最终主力 ASR 是 Paraformer（78MB，手册推荐），那么「Paraformer + 标点模型」用 150MB 拿到 14/24，比再挂一个 228MB 的 SenseVoice 只做决策更划算。**但这会改变主 ASR 选型，需要一起决策。**

**调研方向**：按目标硬件内存预算给一张「总内存 → 可用方案 → 预期质量」的表。
**验收**：给出明确推荐（含放弃项）。

## P2 — 评测本身不够硬

### 9. 测试集太小、太干净

`benchmark/semantic/` 是 MeloTTS 合成的 3 段对话、24 句、**单一音色**、无噪声、无多人、无插话。数字只能说明方向。

**调研方向**：录一份真人对话集（≥100 句，2–3 人，含思考停顿、抢话、方言/口音、背景噪声），人工标注句边界。
**验收**：同一套指标在新集上复现，且给出与合成集的差异分析。

### 10. 参数只扫了一维

只扫过 `short_wait`（见第 0 节）。`mid_wait=0.6`、`long_wait=1.2`、`max_utt=20`、`min_silence=0.1`、`pad=0.2` 都是拍的。其中 `min_silence=0.1` 直接决定片段数（75 片段/272s），进而决定决策成本（问题 7）。

**调研方向**：多维联合搜索（分层或贝叶斯），目标函数同时含「完全切对」「句末等待」。
**验收**：给出帕累托前沿（质量 vs 延迟），而不是单点最优。

### 11. 指标是几何判分，不是用户感受

现在的「切断/粘连」按时间段重叠算。但用户真正痛的是：**抢话**（我说到一半它接话）和**反应慢**（我停下来它半天不吭声）。几何判分和这两个感受没有直接映射。

**调研方向**：定义可测的代理指标，例如「用户未说完就断句的比例」（需要真人标注"说完"时刻），以及「说完到系统断句的 P50/P95 延迟」。
**验收**：给出这两个指标在现有几种切段方式上的数值。

## P3 — 待查证的事实

### 12. Paraformer 单段长度上限到底是多少

28.2s 音频一次喂进去只输出前 ~14s 的内容（32 字），分段喂就正常。**是 sherpa-onnx 的 `OfflineRecognizer` 有分块限制，还是 Paraformer 模型本身的位置编码上限？**

**调研方向**：查 sherpa-onnx 文档/源码中 OfflineRecognizer 对长音频的处理；用 5/10/15/20/30s 切片做二分定位拐点。
**验收**：给出拐点秒数和根因，并说明 `CHUNK_SEC=30` 该不该改。

### 13. 要不要上 turn-detection 小模型

`docs/semantic-seg.md` 第 5 节提过。目前没调研：有没有支持中文、能跑端侧 ONNX、体积小的「话轮结束检测」模型（学术界的 turn detection / end-of-turn detection）。

**调研方向**：找候选（含许可证、体积、是否中英混）、在 24 句集 + 真人集上对比现有规则法。
**验收**：给出「用 / 不用」的结论和理由，若用则给出集成方案。

### 14. 语气词 vs 口头禅无法区分

「呢」在有些人嘴里是句尾语气词（`还有很多很多的朋友呢。` = 完整），在另一些人嘴里是句中填充词（`现场呢来了很多人`）。当前规则只看最后一个字，无法区分。

**调研方向**：能否用时长/音高特征区分（句尾的「呢」通常拖长、音高下降）？或结合「该句已累计时长」（超过 10s 还以语气词结尾，更可能是口头禅）。
**验收**：给出可量化的区分方法，误判率低于现方案。
