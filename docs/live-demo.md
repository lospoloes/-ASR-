# 持续监听 · 双模型并行实时转写（2026-11-04）

> 和 mentor 对齐后的需求：陪伴机器人 24 小时听人聊天，**由 VAD 决定把哪段聊天切成 chunk**，交给 ASR 转写成文本（之后交给大模型，本次不做）。
> SenseVoice-Small int8 和 Paraformer-zh-small int8 是**平行候选**，都是非流式模型。demo 要在"持续聊天"场景下**分别评测**两者，再决定选哪个。

## 1. 怎么用

```bash
python server.py          # 启动后打开 http://127.0.0.1:8000/live（单句对比页顶部也有入口）
```

- 点「**开始监听**」后不用按键，直接聊天。每说完一句，表格里就多一行，左边是 SenseVoice、右边是 Paraformer。
- 说话时会显示「🎙 正在说话 x.x 秒」。
- 没人陪聊时，点「**用音频文件模拟**」选一个 wav，浏览器会按真实速度播放并推流，效果和对着麦克风说一样。
- 可调参数：**切段静音阈值**（0.3 / 0.5 / 0.8 秒）、**最长 chunk**（10 / 15 / 20 秒）、勾选要比较的模型。
- 底部汇总每个模型的 chunk 数、平均 / P90 / 最大延迟、RTF；可导出两个模型的转写文本和全部事件 JSON。
- 每条转写也会追加到 `logs/live/<时间>.jsonl`（模拟"24 小时本地缓存"，不提交到仓库）。

## 2. 方案

两个模型都不是流式的，但仍然可以做到"边聊边出字"：**让 VAD 实时判断一句话什么时候说完，每说完一句就转写一句。**

```
浏览器麦克风（或音频文件）─► 16kHz Int16，每 ~0.1s 一帧 ─► WebSocket /ws/live
   ─► LiveSession：流式 VAD（每会话独立）
        · 有人说话 → 推「正在说话」
        · 静音达到阈值 / 超过最长时长 → 切出一个 chunk（前后各补 0.2s，防吞字）
   ─► 后台线程：同一个 chunk 依次交给 SenseVoice、Paraformer 转写 ─► 文本推回页面
```

- **两个模型拿到完全相同的 chunk**，各自独立转写，对比是公平的。
- **延迟按"单独部署"计算**：VAD 判停等待的静音 + 本模型的解码时间。（demo 里两个模型排队跑，后跑的那个在页面上出字会晚一点，但产品里只会部署其中一个。）
- **VAD 自动增益**：轻声或远场时，Silero 的人声概率贴近阈值，可能整句被丢掉。实测一句 -40dBFS 的话在 Int16 输入下被丢掉，放大 1.3 倍后恢复。所以送进 VAD 前按最近几秒的峰值自动放大（最多 10 倍，只放大不缩小）；纯噪声放大 10 倍也不会误触发。送给 ASR 的仍是原始音频。

代码：`live_engine.py`（核心，和网页无关，可以直接搬到端侧）、`server.py` 的 `/ws/live`、`web/live.html`。

## 3. 评测：持续聊天场景下的两个模型

`python live_sim.py`：把音频按 0.1 秒一块流式喂给同一个 `LiveSession`，和网页走同一套逻辑。完整结果见 `benchmark/results/live.md`。

- **真实延迟** = 用户实际说完 → 该模型出字。只在句尾精确已知的合成对话上统计（3 段共 24 句，生成时已裁掉 TTS 首尾静音）。
- CER 在全部数据上统计：合成对话 3 段、双人对话、雷军 272 秒真人演讲。

| 静音阈值 | SenseVoice CER | Paraformer CER | SenseVoice 真实延迟 | Paraformer 真实延迟 | 雷军演讲 chunk 数（平均时长） |
|---|---|---|---|---|---|
| 0.3s | **3.17%** | 4.41% | 551 ms | **475 ms** | 65（2.5s） |
| **0.5s（默认）** | **3.17%** | 4.07% | 756 ms | **650 ms** | 53（3.1s） |
| 0.8s | **3.39%** | 3.51% | 1047 ms | **895 ms** | 39（4.4s） |

雷军真人演讲单独看（静音阈值 0.5s）：SenseVoice 1.16%、Paraformer 1.50%。

### 结论

1. **SenseVoice 更准**：三种阈值下 CER 都更低，0.5s 时低约 0.9 个百分点。阈值越小（chunk 越碎），Paraformer 掉得越多，说明它更依赖上下文。
2. **Paraformer 更快，但只快约 0.1 秒**：两者的延迟差就是解码时间差（例如 2 秒的 chunk，SenseVoice 约 130ms，Paraformer 约 45ms）。**延迟的大头是"等静音判断说完"**，由静音阈值决定，和选哪个模型关系不大。
3. **静音阈值是主要的调节旋钮**：0.3s 出字最快，但一句话更容易被切碎（合成对话 24 句里有 9 句被切成多段）；0.8s 切得完整，但每句话要多等约 0.3 秒，而且相邻两句更容易粘在一起。**默认 0.5s 是折中。**
4. 对选型的含义：如果端侧算力够（SenseVoice 体积 228MB、解码约慢 3 倍），**SenseVoice 的准确率优势在持续聊天场景下依然成立**，额外延迟只有约 0.1 秒；如果体积 / 算力受限，Paraformer 准确率差得不多。最终还需要在目标芯片上测解码速度。

## 4. 已知局限

- **很短的话可能整句丢失**：合成对话里"等一下（0.5 秒左右）"两个模型都没出字，原因是 VAD 没把它判为人声（`min_speech_duration` 等参数可以再调）。
- **纯 VAD 只看停顿**：会出现"把客厅的灯 | 关掉我觉得这个电影还挺好看的"这种把上一句尾巴接到下一句的情况。之前做的语义切段（`docs/semantic-seg.md`）可以接进来改善，本次没有接。
- **最长 chunk 是软限制**：sherpa-onnx 的 `max_speech_duration` 到时会降低判停门槛，而不是硬切。雷军演讲在 15 秒上限下，实测最长 chunk 为 17.5 秒（静音阈值 0.8s 时），对两个模型都没有影响。
- 测试数据以合成语音为主，真人只有雷军一段单人演讲。**两个人真实聊天的录音**（插话、抢话、远场）还需要实测，demo 页面可以直接录。
- 延迟只算了"判停 + 解码"，没有算浏览器采集和网络传输（本机通常是几十毫秒）。
