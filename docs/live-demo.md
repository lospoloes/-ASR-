# 持续监听 · 双模型并行实时转写（2026-11-04；11-05 换成自己的 VAD、做了实时蹦字）

> 和 mentor 对齐后的需求：陪伴机器人 24 小时听人聊天，**由 VAD 决定把哪段聊天切成 chunk**，交给 ASR 转写成文本（之后交给大模型，本次不做）。
> SenseVoice-Small int8 和 Paraformer-zh-small int8 是**平行候选**，都是非流式模型。demo 要在"持续聊天"场景下**分别评测**两者，再决定选哪个。
>
> 11-05 补充：按项目计划书（Voice Agent OS V3.7.0），本仓库负责上游的 **VAD 和 ASR**，交给 V4 的是第 5 节的事件接口（对应计划书 §7.2 V4-01 列的五项）。会议纪要定的方向：VAD 静音检测切分、最长 8 秒强制切断，先识别输出临时结果，整句说完后全量重识别替换；"算力换延迟"，出字延迟从一句话降到几个音节。

## 1. 怎么用

```bash
python server.py          # 启动后打开 http://127.0.0.1:8000/live（单句对比页顶部也有入口）
```

- 点「**开始监听**」后不用按键，直接聊天。每说完一句，表格里就多一行，左边是 SenseVoice、右边是 Paraformer。
- 说话时会显示「🎙 正在说话 x.x 秒」。
- 没人陪聊时，点「**用音频文件模拟**」选一个 wav，浏览器会按真实速度播放并推流，效果和对着麦克风说一样。
- 可调参数：**切段静音阈值**（0.3 / 0.5 / 0.8 秒）、**最长 chunk**（10 / 15 / 20 秒，到了就硬切）、**实时出字**（关 / 0.25 / 0.4 / 0.5 / 0.6 / 1 秒，默认 0.5）、勾选要比较的模型。
- **实时出字**：一句话还没说完，表格里就先多出一行（标着「说话中…」），字分三种颜色：
  - **浅灰**：正在说的这一段，每 0.5 秒重新识别一次，会变；
  - **深灰**：已经锁定的段。句内停顿 ≥0.2 秒（或一段长到 8 秒）时切开，整段识别一次，之后不再变；
  - **黑**：正式结果。VAD 判定这句说完后，整句重新识别一遍，替换这句的全部灰字。
  底部汇总多一列「实时出字」：识别了几次、额外花了多少解码时间。
- 底部汇总每个模型的 chunk 数、平均 / P90 / 最大延迟、RTF；可导出两个模型的转写文本和全部事件 JSON。
- 每条转写（包括临时结果）也会追加到 `logs/live/<时间>.jsonl`（模拟"24 小时本地缓存"）；录音同时存为同名的 `logs/live/<时间>.wav`（16kHz 单声道，约 1.9MB/分钟）。录音的第 0 秒就是会话开始，和 jsonl 里每个 chunk 的 start / end 对齐，可以拿来换静音阈值或切段方式重跑。两者都只在本机，不提交到仓库；不想存录音就用 `python server.py --no-save-audio`。

## 2. 方案

两个模型都不是流式的，但仍然可以做到"边聊边出字"：**让 VAD 实时判断一句话什么时候说完，每说完一句就转写一句；没说完时，把正在说的这一小段反复重新识别，先出临时结果。**

```
浏览器麦克风（或音频文件）─► 16kHz Int16，每 ~0.1s 一块 ─► WebSocket /ws/live
   ─► LiveSession：vad_stream 逐帧（32ms）跑 Silero，每帧一个人声概率（每会话独立）
        · 开口：概率 >0.5 持续 0.15s → speech_start；说话中每 0.5s 推一次 speaking（带平均概率）
        · 切段：句内停顿 ≥0.2s（且这段已 ≥1s），或一段长到 8s（硬切）→ cut
        · 切句：静音 ≥ 阈值（默认 0.5s），或一句长到上限（默认 15s，硬切）→ chunk（句首句尾各补 0.2s，防吞字）
   ─► 转写线程，优先级：正式结果 > 段锁定 > 蹦字
        · 正式结果：整句依次交给 SenseVoice、Paraformer ─► 黑字，替换这句的全部临时文字
        · 段锁定：刚切下来的那一段识别一次 ─► 深灰，之后不再变
        · 蹦字：当前这一段每 0.5s（页面默认）从段起点重新识别一次 ─► 浅灰（只留最新一份，过期就作废）
```

- **两个模型拿到完全相同的 chunk**，各自独立转写，对比是公平的。
- **延迟按"单独部署"计算**：VAD 判停等待的静音 + 本模型的解码时间。（demo 里两个模型排队跑，后跑的那个在页面上出字会晚一点，但产品里只会部署其中一个。）
- **实时出字为什么按段**：离线模型不能接着上次的结果往下算，每次都得从头识别。第一版（3.2 节）每 1 秒把整句从头识别一遍，算力随句长平方增长，16 秒的长句累计要识别 128 秒音频。现在只重识别**当前这一段**：段在句内停顿处切开，最长 8 秒，所以单次识别不超过 8 秒音频，算力和句长成正比。切下来的段识别一次就锁定，整句说完再整句识别一次出正式结果。实现上保证三件事：**正式结果优先**（有正式结果要做时，段锁定和蹦字都让路）；**蹦字只留最新一份**（忙不过来时旧的被新的覆盖，不会越积越多）；**同一句的临时结果一定先于正式结果到达**（正式结果不会被临时结果盖掉）。
- **自己跑 VAD（`vad_stream.py`）**：sherpa-onnx 的 VAD 在 Python 里只给"是不是在说话"，不给概率；它的"最长时长"是软限制（到时只放宽判停条件，实测切出过 16.2 秒的段）。现在用 onnxruntime 逐帧跑同一个 `silero_vad.onnx`，判定规则逐句照搬 sherpa：用 sherpa 的参数时，切出的句子和 sherpa **逐帧一致**（单元测试对照；177 秒真人对话上 27/27 段起止一个采样点都不差）。在此之上加了：每帧的人声概率；句内按停顿切段；段和句到上限都硬切，切在最近 2 秒里概率最低的那一帧；"开口后概率低于多少开始计静音"可调。默认参数是在 94 分钟真人对话上评测后定的（3.3 节）。
- **VAD 自动增益**：轻声或远场时，Silero 的人声概率贴近阈值，可能整句被丢掉。实测一句 -40dBFS 的话在 Int16 输入下被丢掉，放大 1.3 倍后恢复。所以送进 VAD 前按最近几秒的峰值自动放大（最多 10 倍，只放大不缩小）；纯噪声放大 10 倍也不会误触发。送给 ASR 的仍是原始音频。真人对话上关掉增益，误检多一倍、超长硬切多两倍（3.3 节）。

代码：`vad_stream.py`（VAD）、`live_engine.py`（核心，和网页无关，可以直接搬到端侧）、`server.py` 的 `/ws/live`、`web/live.html`。

## 3. 评测：持续聊天场景下的两个模型

`python live_sim.py`：把音频按 0.1 秒一块流式喂给同一个 `LiveSession`，和网页走同一套逻辑。完整结果见 `benchmark/results/live.md`。

- **真实延迟** = 用户实际说完 → 该模型出字。只在句尾精确已知的合成对话上统计（3 段共 24 句，生成时已裁掉 TTS 首尾静音）。
- CER 在全部数据上统计：合成对话 3 段、双人对话、雷军 272 秒真人演讲。

| 静音阈值 | SenseVoice CER | Paraformer CER | SenseVoice 真实延迟 | Paraformer 真实延迟 | 雷军演讲 chunk 数（平均时长） |
|---|---|---|---|---|---|
| 0.3s | **3.17%** | 4.41% | 551 ms | **475 ms** | 65（2.5s） |
| **0.5s（默认）** | **3.17%** | 4.07% | 756 ms | **650 ms** | 53（3.1s） |
| 0.8s | **3.39%** | 3.51% | 1047 ms | **895 ms** | 39（4.4s） |

雷军真人演讲单独看（静音阈值 0.5s）：SenseVoice 1.16%、Paraformer 1.50%。

上表的延迟是在云端开发环境里测的。同一套评测在 Mac（Apple M4 Pro，每个模型 2 线程）上重跑，CER 基本不变；默认 0.5s 时真实延迟为 SenseVoice 653 ms、Paraformer 617 ms。解码越快，两个模型的差距越小（这里只差约 36 ms）。

### 结论

1. **SenseVoice 更准**：三种阈值下 CER 都更低，0.5s 时低约 0.9 个百分点。阈值越小（chunk 越碎），Paraformer 掉得越多，说明它更依赖上下文。
2. **Paraformer 更快，但只快约 0.1 秒**：两者的延迟差就是解码时间差（例如 2 秒的 chunk，SenseVoice 约 130ms，Paraformer 约 45ms）。**延迟的大头是"等静音判断说完"**，由静音阈值决定，和选哪个模型关系不大。
3. **静音阈值是主要的调节旋钮**：0.3s 出字最快，但一句话更容易被切碎（合成对话 24 句里有 9 句被切成多段）；0.8s 切得完整，但每句话要多等约 0.3 秒，而且相邻两句更容易粘在一起。**默认 0.5s 是折中。**
4. 对选型的含义：如果端侧算力够（SenseVoice 体积 228MB、解码约慢 3 倍），**SenseVoice 的准确率优势在持续聊天场景下依然成立**，额外延迟只有约 0.1 秒；如果体积 / 算力受限，Paraformer 准确率差得不多。最终还需要在目标芯片上测解码速度。**注意：3.1 节的真人对话里，这个优势没有复现。**

### 3.1 真人双人对话实测（2026-11-05，Mac）

合成对话太"整齐"：句间停顿清楚，一次只有一个人说话。所以又从网上找了一段公开的**真人自由聊天**：MagicData-RAMC（两人面对面聊天、手机录制，人工转写到句，带起止时间和说话人；许可证 CC BY-NC-ND 4.0，音频和文本只放在本机，不提交）。截取 dev 集一段对话的 177 秒：两位女性聊"数学"，53 句、739 字（去标点），换人 21 次。句间空隙中位数只有 0.41 秒，52 处里有 32 处不到 0.5 秒，听的一方经常插一句"嗯"。

跑了两遍，结果一致：
- 按真实速度推给 `server.py` 的 `/ws/live`（和网页同一条路径）：177 秒切出 28 段，第 2.5 秒出第一行字，两个模型各出 28 条，没有报错。
- `python live_sim.py --real` 离线跑三种静音阈值（完整结果见 `benchmark/results/live_real.md`）：

| 静音阈值 | chunk 数（平均 / 最长） | SenseVoice CER | Paraformer CER | SenseVoice 真实延迟 | Paraformer 真实延迟 | 一段含两人 |
|---|---|---|---|---|---|---|
| 0.3s | 43（3.5s / 11.6s） | 6.36% | **5.41%** | 412 ms | **366 ms** | 9 |
| **0.5s（默认）** | 28（5.6s / 16.2s） | 5.82% | **5.41%** | 573 ms | **509 ms** | 7 |
| 0.8s | 17（9.7s / 18.5s） | **5.68%** | 5.82% | 651 ms | **560 ms** | 8 |

真实延迟 = 人工标注的句尾 → 出字，只统计 VAD 正好在句尾切开的句子（0.5s 时 28 句）。机器：Apple M4 Pro，每个模型 2 线程。

> **下午换成新 VAD 后重跑**（3.3 节的默认参数，`live_sim.py --real`，完整结果见 `benchmark/results/live_real.md`），并用 `fetch_ramc.py --count 3` 从同一 dev 集另外两段对话各截了约 3 分钟：
> - 1434 这段，静音阈值 0.5s：SenseVoice 5.68%、Paraformer 5.68%，真实延迟 556 / 493 ms。CER 的变化在噪声内（3.4 节第 5 条）。
> - 三段合计，0.5s：SenseVoice 4.76%、Paraformer 5.08%，真实延迟 559 / 509 ms。
> - 真实延迟现在只统计**静音判停**的句子，长到 15 秒被硬切的不计：那时人还在说，硬切的判定时刻比切点晚最多 2 秒，算不上"说完到出字"。上表 0.8s 一行用的是 sherpa 的软上限：超长以后静音 0.1 秒就切，等得短，所以那一行的延迟偏低。新 VAD 下 0.8s 时 1434 这段是 813 / 748 ms。
> - 新截的 1422 那段是长段独白加对方的"嗯"，0.5s 时 19 句里有 8 句长到 15 秒被硬切。

**两个模型各自的明显错误**（默认 0.5s，和人工标注逐字对齐）：
- **大部分错误两个模型犯在同一处**：错误片段 SenseVoice 35 处、Paraformer 33 处，其中 28 处位置相同。
- **约四分之一不影响理解**：标注里的儿化音（"学科儿""语文儿"等）两个模型都不写出来，各 5 处；"它"写成"他"各 5 处。去掉这两类后，SenseVoice 4.50%、Paraformer 4.09%。
- **共同的实际错误**："奥数班"→"二数班"；"应是"→"已经是"；"比起你小学"→ SenseVoice "比起林教学"、Paraformer "比基尼教学"。另有几处两个模型一致、但和标注不同（如"暴露了一些定理"→"告诉你一些定理"），可能是标注本身的问题，没有逐一听音核实。
- **SenseVoice 独有**："学高数"→"写高数"、"浅显"→"浅浅"、"什么样"→"什面"。
- **Paraformer 独有**：更容易漏掉对方插的短"嗯"（4 处，SenseVoice 2 处）；"学生嘛"→"学生们"。

**结论**

1. **真人聊天里两个模型准确率很接近，Paraformer 不比 SenseVoice 差**：默认 0.5s 时 5.41% 对 5.82%，739 字里只差 3 个字。合成数据上"SenseVoice 更准"的结论在这段真人对话里没有复现。只有一段 3 分钟，差距在误差范围内，还不足以改选型，但说明**合成数据会放大 SenseVoice 的优势**，选型要靠更多真人录音。
2. **最大的问题是切段，不是转写**：
   - **两个人的话被并进同一段**：0.5s 时 28 段里有 7 段同时含两个人的话，多是一方说完另一方马上接，或者边听边"嗯"。比如 B 刚说完一句感想，A 马上接着反问、讲起自己的经历，两句被切成一段、转成一句话，交给大模型时分不清是谁说的。把阈值调到 0.3s 也没有减少（9 段），因为很多换人间隔本来就不到 0.3 秒。要分清说话人，得接分角色（说话人分离或说话人切换检测），只调静音阈值解决不了。
   - **"持续出字"打了折扣**：合成对话里每 1–5 秒出一段；真人聊天的停顿被"嗯"和接话填满，0.5s 时 28 段里有 5 段超过 10 秒，页面上最长 **16.9 秒没有新字**（B 连续说了 16 秒，中间只有 A 插的"嗯"）。把"最长 chunk"从 15s 调到 6s，最长等待只降到约 10.5 秒（当时用 sherpa 的 VAD，上限是软的；现在已改成硬切，见第 2 节），CER 基本不变（两者都是 5.55%）。要做到"边聊边出字"，得在一句话还没说完时就出临时结果：比如每 1–2 秒对正在说的这一段重跑一次识别，先显示灰色的临时文本，切段后再换成正式结果；或者到上限就硬切。**实时出字已经做了，实测见 3.2、3.4 节。**
3. **延迟仍由静音阈值决定**：真实延迟 ≈ 阈值 + 解码。真人对话的 chunk 更长，两个模型的解码差距比合成数据大（每段平均解码 SenseVoice 123 ms、Paraformer 38 ms），Paraformer 快约 45–90 ms。
4. 这段是手机近讲录音，条件比陪伴机器人的远场好；远场还得自己录（见第 4 节）。

### 3.2 临时出字第一版：整句重识别（2026-11-05，Mac）

> 第一版是每隔 1 秒把正在说的**整句**从头识别一遍，已被 3.4 节的按段实时出字取代，这里保留作对照。

还是 3.1 节那段 177 秒的真人对话。这次用 `tools/replay_live.py` 按真实速度推给 `server.py` 的 `/ws/live`（和网页同一条路径，0.1 秒一块），记下每个事件到达的时刻。不开、每 1 秒、每 2 秒各跑一遍，静音阈值 0.5s，Apple M4 Pro，每个模型 2 线程。完整结果见 `benchmark/results/live_partial.md`。

- **开口后见字**：一句话（VAD 切出的 chunk）开始 → 屏幕上出现这句的第一个字，临时或正式都算
- **说话时屏幕落后**：有人说话的每个时刻（按人工标注，每 0.1 秒取一点），屏幕上的字只识别到了多少秒之前的话
- **最长没有新字**：相邻两次更新之间的最长间隔，和 3.1 节的 16.9 秒同一口径

| 临时出字 | 开口后见字（平均 / 最长） | 说话时屏幕落后（平均 / P90 / 最大） | 最长没有新字 | 正式结果出字（平均 / 最大） |
|---|---|---|---|---|
| 不开 | 6.2 / 16.7 s | 5.6 / 11.2 / 17.5 s | 16.9 s | SenseVoice 606 / 748 ms，Paraformer 643 / 832 ms |
| **每 1 秒（默认）** | **1.3 / 1.4 s** | **0.7 / 1.4 / 2.9 s** | **2.4 s** | SenseVoice 610 / 851 ms，Paraformer 647 / 933 ms |
| 每 2 秒 | 2.1 / 2.5 s | 1.3 / 2.4 / 3.9 s | 3.4 s | SenseVoice 605 / 756 ms，Paraformer 648 / 865 ms |

前三项两个模型相差不到 0.1 秒，表里列的是排在后面跑的 Paraformer。"正式结果出字"是 VAD 判停 → 正式结果到达，含排队。Paraformer 排在 SenseVoice 后面跑，要多等 SenseVoice 的解码；产品里只部署一个模型，就没有这部分。

| 临时出字 | 模型 | 临时识别次数 | 额外解码（正式结果的几倍） | 转写占用（解码耗时 / 音频时长） | 灰字后来被改 |

| 每 1 秒 | Paraformer | 137 | 4.7 倍 | 3.3% | 1.1% |
| 每 2 秒 | SenseVoice | 65 | 2.4 倍 | 6.2% | 0.8% |
| 每 2 秒 | Paraformer | 63 | 2.3 倍 | 1.9% | 1.4% |

三遍的正式结果逐字相同，CER 仍是 SenseVoice 5.82%、Paraformer 5.41%。

**结论**

1. **"边聊边出字"基本解决**：每 1 秒出一次临时结果后，开口后 1.3 秒就能看到字；不开时平均要等 6.2 秒，最长 16.7 秒。说话时屏幕上的字平均只落后 0.7 秒，最长没有新字从 16.9 秒降到 2.4 秒。28 段里 23 段出了灰字。没出的 5 段都不到 0.7 秒（多是"嗯"），说完就出正式结果。
2. **正式结果几乎不受影响**：平均只慢 3–4 ms，文本和不开时逐字相同。28 段里只有 1 段慢了 50 ms 以上（约 110 ms）：这句说完时，手上正好有一次临时识别没做完，正式结果要等它做完。
3. **代价是算力，而且随句长平方增长**：离线模型每次都要从头识别。最长那段 16.2 秒，每 1 秒一次，15 次临时识别累计识别了 128 秒音频，约是正式结果的 8 倍。整段对话下来：
   - SenseVoice 的解码总量变成原来的 6 倍，转写占用从 1.9% 升到 11.3%；
   - Paraformer 从 0.6% 升到 3.3%；
   - 改成每 2 秒一次，额外解码减半，屏幕平均落后 1.3 秒，最长没有新字 3.4 秒。
4. **灰字很稳**：临时结果里约 1% 的字后来被改掉。一部分是句尾没听完的半个词（"出"→"初中"）；更多是听到后文后改了前面的字（"奥书班"→"奥数班"），偶尔会来回改（"到大学"↔"到了大学"）。
5. **对端侧的含义**：M4 Pro 很快，换到目标芯片上解码会慢好几倍，转写占用也按比例放大。比如解码慢 5 倍时，每 1 秒一次的临时出字，SenseVoice 要占约 57% 的时间，Paraformer 约 17%（按上表估算，没有实测）。忙不过来时，临时识别只会被跳过（槽位只留最新一份），不会积压。但句子越长，单次临时识别越慢，正式结果最多要多等一次：这段对话里 SenseVoice 最慢的一次是 280 ms，慢 5 倍就是 1.4 秒。建议：
   - 只给最终选定的那个模型开临时出字；
   - 间隔用 2 秒，或者句子越长间隔越大、只重识别最近几秒；
   - 长远看，用流式模型出临时结果、离线模型出正式结果（FunASR 的 2pass 就是这个思路），临时识别的算力和句长成正比，而不是平方。

### 3.3 VAD 评测：94 分钟真人对话（2026-11-05）

会议纪要说优化方向是"做好 VAD"。VAD 决定三件事：
- 什么时候算开口：影响多快出字，以及"嗯""好"这类短句会不会丢；
- 什么时候算说完：影响正式结果多快出，以及相邻两句会不会粘在一起；
- 句内在哪里切段：影响实时出字的算力。

**数据**：MagicData-RAMC dev 集前 3 段**整段**对话（`python tools/fetch_ramc.py --count 3`），共 94 分钟、1647 句人工标注，其中 249 句不到 0.8 秒。都是手机近讲录音、两人面对面闲聊，但录音条件不同：1447 很干净，不说话时人声概率几乎是 0；1422 和 1434 有底噪，不说话时概率常在 0.3–0.5。

**方法**：`tools/eval_vad.py`。每段对话的逐帧人声概率只算一遍，各组参数拿同一串概率重放切分，再和人工标注对照。完整结果见 `benchmark/results/vad_eval.md`（只有统计数字）。指标：
- 开口延迟：前面 ≥1 秒没人出声的句子，从标注起点到 VAD 确认开口；
- 判停延迟：后面 ≥1 秒没人出声的句子，从标注终点到 VAD 判定说完；
- 漏检：标注句被 VAD 覆盖不到一半；括号里是其中不到 0.8 秒的短句；
- 误检：VAD 判为说话、但离所有声音标注都超过 0.3 秒的时长；
- 并进下一句：后面明明空了 ≥1 秒，VAD 却没判停，和下一句连成一句；
- 混说话人：VAD 的一句里，两个人各有 >0.1 秒的话。

标注起止本身有零点几秒误差，只看中位数、P90 和各组之间的差。

**发现：有底噪时判停晚。** sherpa（和 Silero 官方）的规则是：开口以后，概率只要高于 0.35（阈值 0.5 − 0.15）就算还在说，降到 0.35 以下才开始计静音。有底噪的两段里，说完话后概率要一秒多才从 1 降到 0.35 以下，这段时间一直不计静音。结果：
- 判停晚：1422 的判停延迟中位数 1.05 秒，而静音阈值只有 0.5 秒；
- 相邻两句容易连成一句，甚至一直连到 15 秒上限被硬切。

**取舍**

1. **最短开口 0.25 → 0.15 秒**：开口早约 0.09 秒，漏检从 11 句降到 4 句（短句 7 → 3），误检没有增加。0.1 秒在这批数据上还略好一点（漏检 3 句、开口 0.22 秒），但 RAMC 里没有关门、碗碟这类短促的家庭噪声，开口门槛越低越容易被它们触发，所以先取 0.15。
2. **静音阈值 0.35 → 0.5**（开口后概率一低于 0.5 就开始计静音）：
   - 有底噪的两段，判停中位数早约 0.2 秒；
   - 误检减半（27 → 14 秒/小时）；
   - 相邻两句连成一句从 11 处降到 4 处，长到上限的句子从 144 降到 119。

   代价是漏检多 1–2 句、标注语音覆盖率降 0.2 个百分点（98.1% → 97.9%）。干净的录音不受影响。
3. **其余不改**：
   - 阈值 0.4：漏检少一半，但误检多 55%，长到上限的句子多 17%。0.6：漏检翻倍。阈值保持 0.5。
   - 句末静音 0.3 秒：判停快 0.2 秒，但一句话被切成两段的从 115 句增加到 249 句。0.8 秒：32% 的句子混了两个人。这一项是页面上的选项，默认仍是 0.5 秒。
   - 段停顿 0.15 / 0.3 秒：只影响实时出字的算力，估算额外解码 6.9 / 7.6 倍（0.2 秒时 7.2 倍；按每 0.5 秒蹦字、3.4 节实测的解码开销估）。没有段锁定准确率的数据，先不动。
   - 自动增益保留：关掉后误检多 90%，长到上限的句子多 50%。
4. **VAD 解决不了混说话人**：新默认下仍有 16% 的句子同时含两个人的话，多是一方说话时另一方插"嗯"，或者接话太快。只调 VAD 降不下来（句末静音 0.3 秒时仍有 11%），要靠说话人切换检测。
5. **切段情况**：新默认下平均每句 1.7 段，段长中位数 2.3 秒、P90 6.4 秒；停顿切了 1290 刀，8 秒硬切 130 刀。有一半的停顿切点之后这句就结束了（"句尾空切"），那次段锁定的结果 0.3 秒后就被正式结果替换，白做了，暂不优化。

对照计划里定的目标：

| 指标 | 目标 | 第一版（整句，每 1 秒） | 按段，每 0.5 秒（默认） |
|---|---|---|---|
| 开口后见字（平均） | ≤0.6 s | 1.3 s | **0.5 s** ✓ |
| 说话时屏幕落后（平均 / P90） | ≤0.5 / ≤0.8 s | 0.7 / 1.4 s | **0.3 / 0.5 s** ✓ |
| 最长没有新字 | ≤1.5 s | 2.4 s | **1.5 s** ✓ |
| 临时识别单次最长音频 | ≤8.4 s | 15.9 s | **8.1 s** ✓ |
| SenseVoice 额外解码 | ≤8 倍 | 5.0 倍 | **7.3 倍** ✓ |
| 正式结果 CER 变化 | ≤0.2 个百分点 | SenseVoice 5.82%、Paraformer 5.41% | 都是 5.68%：SenseVoice −0.14 ✓，Paraformer +0.27 ✗（在测量噪声内，见第 5 条） |

**结论**

1. **出字延迟降到了"几个音节"**：默认每 0.5 秒时，开口后 0.5 秒就能看到字（第一版 1.3 秒），说话时屏幕平均只落后 0.3 秒。"最长没有新字"的 1.5 秒出现在 109 秒处，那里两句之间本来就有 1.48 秒没人说话。
2. **默认间隔从计划的 0.4 秒改成 0.5 秒**：
   - 0.4 秒时延迟指标都达标，但 SenseVoice 额外解码 8.8 倍，超了 8 倍的上限。计划估的是 7.7 倍：实时链路里识别是零散的，每次的固定开销约 28 ms，而离线连续跑时只有约 11 ms。
   - 计划里的退路是改成 0.6 秒，但实测 0.6 秒时最长没有新字 1.7 秒、Paraformer 开口后见字 0.7 秒，超了目标。
   - 所以加测了 0.5 秒：全部达标。页面上 0.25 / 0.4 秒仍然可选。
3. **单次识别不再随句长变长**：第一版单次最长要识别 15.9 秒音频，现在不超过 8.1 秒。每 0.5 秒时一共 339 次临时识别（其中 45 次段锁定），单次平均 2.6 秒音频。算力和句长成正比，不再是平方关系。
4. **正式结果不受实时出字影响**：每种间隔下，正式结果都和不开时逐字相同，平均出字时间相差不到 10 ms。正式结果出字的最大值从 0.75 秒变成 1.12 秒，来自唯一一处 15 秒硬切：切点取在判定时刻之前 0.88 秒（最近 2 秒里概率最低处），这个指标从切点算起。按音频时间算，这句的正式结果反而比第一版早到 1.3 秒。
5. **CER 的变化在测量噪声内**：换 VAD 后，28 段里 27 段的起止只差 0.03 秒以内，正式结果的差别来自模型对切点很敏感。把第一版的 28 个切点整体挪 16–32 ms 重新识别，SenseVoice 的 CER 在 5.01%–6.22% 之间变，Paraformer 在 5.01%–6.09% 之间变；只把切点四舍五入到 0.01 秒，Paraformer 就从 5.41% 变成 5.82%。所以在这段 739 字的对话上，±0.6 个百分点以内的差别都是噪声，计划里"变化 ≤0.2 个百分点"定得比测量精度还细。3.1 节"Paraformer 5.41% 对 SenseVoice 5.82%"的差别也在噪声内：要比较两个模型，得用更长的数据，比如 3.3 节那 94 分钟整段对话。
6. **灰字改得稍多**：临时结果里有 1.5–1.8% 的字后来被改（第一版 0.9–1.1%）。段更短，每次识别的上下文更少。
7. **对端侧的含义**：每 0.5 秒时，M4 Pro 上 SenseVoice 的转写占用 14.9%、Paraformer 4.2%。目标芯片如果解码慢 5 倍，SenseVoice 就要占约 75%，所以只给最终选定的那个模型开；不够就把间隔调到 1 秒（9.3%）。45 次段锁定里有 20 次是"句尾空切"（锁定完 0.3 秒正式结果就到了），SenseVoice 白做约 0.5 倍，占每 0.5 秒时额外解码的 6%，以后可以省掉。

## 4. 已知局限

- **短句仍可能丢**：最短开口从 0.25 秒降到 0.15 秒后，94 分钟真人对话里漏检从 11 句降到 5 句，其中 3 句是不到 0.8 秒的"嗯""对"（3.3 节）。
- **一句里混两个人**：VAD 切出的句子约 16% 同时含两个人的话（3.3 节）。只调 VAD 参数降不下来，要靠说话人切换检测（这轮没做）。
- **纯 VAD 只看停顿**：会出现"把客厅的灯 | 关掉我觉得这个电影还挺好看的"这种把上一句尾巴接到下一句的情况。语义断句和 endpoint 属于 V4；VAD 只提供概率、停顿（`cut`）和时间。
- **硬切点附近可能切断一个字**：段和句到上限就硬切，切点取最近 2 秒里人声概率最低的那一帧。句子硬切时切点两边都不补 pad，免得同一个字被两句各识别一次，但切点正好落在字中间时，这个字可能两边都识别不全。
- **新默认参数只在 3 段手机近讲录音上定过**：最短开口 0.15 秒会不会被关门、碗碟这类短促的家庭噪声触发，静音阈值 0.5 在远场和电视背景声下表现如何，都还没测。陪伴机器人真正面对的**远场**（人离设备 1–3 米）、多人抢话、电视背景声，还要自己录；demo 页面可以直接录，录音会自动存到 `logs/live/`。
- **实时出字的算力**：按段识别后，单次识别不超过 8 秒音频，算力和句长成正比，不再是平方关系。但间隔越短越贵，到端侧芯片上要先测（3.4 节）。只给最终选定的那个模型开，可以省一半。
- 延迟只算了"判停 + 解码"，没有算浏览器采集和网络传输（本机通常是几十毫秒）。

## 5. 给下游的事件接口（V4-01 上游契约草案）

计划书 §4.2：上游的 VAD / ASR 由本仓库提供；§7.2 要求 V4-01 先定清楚上游给什么。下面是 `live_engine.LiveSession` 现在推出的事件（`/ws/live` 原样转发 JSON），按 §7.2 列的五项对照。

**① VAD 的开始、持续、结束事件**

| 事件 | 字段 | 含义 |
|---|---|---|
| `speech_start` | `t, start, prob` | 有人开口。`t`：VAD 确认的时刻；`start`：往回推的开口时刻（约 `t` − 0.2 秒）；`prob`：确认那一帧的人声概率 |
| `speaking` | `t, dur, prob` | 正在说，每 0.5 秒一次。`dur`：从确认开口到现在多久；`prob`：最近 0.5 秒的平均人声概率 |
| `cut` | `t, chunk_id, piece, at, reason` | 句内切段：第 `piece` 段到 `at` 为止。`reason`：`pause`（停顿 ≥0.2 秒）/ `max_len`（一段长到 8 秒）。V4 判断"说没说完"时，可以把它当作短停顿信号 |
| `speech_end` | `t` | VAD 判定说完了（静音 ≥ `min_silence`，或会话结束）。句子到上限被硬切时**不发**：人还在说 |
| `chunk` | `id, start, end, dur, reason, endpoint_wait_ms` | 切出一句，交给 ASR。`reason`：`silence` / `max_len`（硬切，下一句紧接着从 `end` 开始）/ `flush`（会话结束时还没说完）；`endpoint_wait_ms`：说完到判停等了多久 |

**② 时间戳和语音概率**
- 所有 `t`、`start`、`end`、`at`、`piece_start` 都是**会话音频时间**（秒，第 0 个采样 = 0），不用任何一方的墙钟；服务端存的 `logs/live/<时间>.wav` 和它同一个零点。
- `decode_ms`、`lag_ms`、`latency_ms`、`shown_ms` 是处理耗时（毫秒，墙钟）。
- 人声概率每 32ms 一帧，事件里只带 `speech_start` 那一帧和 `speaking` 的 0.5 秒平均。V4 需要逐帧概率的话，`vad_stream.SileroStream.accept()` 返回的每一帧都有，可以加一个事件推出去。

**③ ASR 的临时结果和最终结果**

| 事件 | 字段 | 含义 |
|---|---|---|
| `partial` | `chunk_id, model, kind, rev, piece, piece_start, start, end, text, locked, live, audio, decode_ms, lag_ms` | 临时结果。`kind`：`live`（蹦字，当前这段的最新识别）/ `lock`（这段已锁定，之后不变）。`text` = `locked` + `live`：`locked` 是已锁定各段的文字，`live` 是当前这段的文字。`start` → `end` 是这句已经识别到的范围 |
| `text` | `chunk_id, model, text, decode_ms, rtf, latency_ms, shown_ms` | 正式结果：整句重新识别 |

**④ 文字改了怎么通知下游**：不发增量（diff），每次都发**这一句当前的完整文字**，下游按 `(chunk_id, model)` 整体替换：
- 同一句、同一模型的 `partial`，`rev` 严格递增，新的整体替换旧的；
- `locked` 只会变长，已锁定的部分在正式结果之前不会再改；`live` 每次都可能整体改写；
- `text` 一到，就替换这句的全部 `partial`，之后这句不会再有 `partial`。

**⑤ 事件顺序和时间对齐**
- VAD 事件按音频顺序同步发出：`speech_start` → `speaking` / `cut` → `speech_end` → `chunk`。
- ASR 事件来自转写线程，比对应的 VAD 事件晚（晚多少看 `lag_ms` / `shown_ms`），但保证：
  - 同一句的 `partial` 一定在它的 `text` 之前；
  - 段锁定按段的顺序出；
  - `text` 按 `chunk_id` 顺序出。
- `partial` 和 `cut` 里的 `chunk_id` 是这句切出来以后会用的编号，所以一句话还没切出来，就能和之后的 `chunk` / `text` 对上。
- 一句的 `chunk` 事件之后，还可能再到一条它的 `partial`（切句时手上正好在做的那次临时识别），之后才是 `text`。

**还没有的**：说话人是谁（换人检测 / 声纹，见 `docs/speaker-id.md`）、语义上的"说完了"（V4 的 endpoint）、逐字时间戳（SenseVoice 能出，还没接）。
